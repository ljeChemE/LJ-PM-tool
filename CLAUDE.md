# CLAUDE.md — Project Context

## What This Repository Is

LJ-PM-tool — a personal project management tool: a daily to-do list combined
with a per-project kanban dashboard, for one user, running locally.

**Status:** In development. Daily to-do list and the project kanban
dashboard are both shipped (backend + frontend).

## Goal & Guiding Principle

Build a tool where capturing or updating a task never costs more than a
couple of seconds and one deliberate action — see
[docs/design/Philosophy.md](docs/design/Philosophy.md) for the full guiding
principle ("never lose a task to friction") and its design failure test.
The daily list and the project dashboard both exist to *look at* work
already captured cheaply; neither is allowed to make capture itself slower.

## Key Design Decisions — and Non-Goals

- **Stack:** React (Vite/TS) frontend + FastAPI (Python) backend + Postgres,
  two services over a CORS-enabled REST API — chosen deliberately (over a
  single-codebase framework) so the client/server boundary stays explicit,
  for learning value.
- **`deadline` is the only date field on a task:** no separate "day"
  concept. It defaults to the task's creation day, doubles as which daily
  list the task is sorted into, and auto-advances to today if missed while
  incomplete (incrementing `carried_over_count`). Guarded by
  `tests/integration/test_task_rollover_guardian.py` — change
  `list_todays_tasks` in `backend/app/main.py`, update that suite in the
  same change.
- **Infrastructure parity:** tests run against real Postgres 16 (same major
  version as dev/CI), never a substitute. `tests/conftest.py` creates and
  migrates a dedicated `<POSTGRES_DB>_test` database automatically.
- **Projects are a fixed set, not user-creatable:** exactly 8 hashtags
  (`OBE`, `WUT`, `RNAP`, `BI`, `ECMC`, `CLU`, `DNR`, `ADMIN`), seeded via a
  data migration (`backend/alembic/versions/5dd55bd6b1ee_...py`) rather than
  a runtime seed script — `just migrate` alone guarantees every environment
  has this exact set. There is no "add project" UI or flow.
- **Tasks have a 3-stage `status`** (`todo` / `in_progress` / `done`),
  replacing an earlier plain boolean `done` — needed for the kanban
  dashboard's three columns. **Projects also have a `status`**
  (`in_progress` / `completed`), independent of their tasks' statuses —
  currently `BI` and `ECMC` are `completed`, the other 6 are `in_progress`.
  Both are plain `String` columns with a DB `CHECK` constraint, not a DB
  enum type, to keep migrations simple.
- **Two task-fetching scopes, three pages:** `TodayView` shows one day's
  tasks via `GET /tasks/today` (rollover-applying). `DashboardView` and
  `ProjectPage` both use `GET /projects/{id}/tasks` — a project's *entire*
  history, no rollover, no day filter — but at different densities:
  `DashboardView` is a lightweight preview row (project name + flat task
  list, click through), `ProjectPage` is the full 3-column kanban board
  with the status-changing dropdown. Don't conflate `/tasks/today` with
  `/projects/{id}/tasks`.
- **No branch protection:** solo project, no second reviewer to satisfy a
  required-approval rule — commits land directly on `main`. CI still runs
  on every push (see Conventions). Revisit if this project gets a second
  contributor.
- **Non-goals (for now):** no auth/multi-user support; no external calendar
  integration ("today" comes from the app's own clock, not e.g. Google
  Calendar); no production frontend build yet (`frontend/Dockerfile` runs
  the dev server, not a built artifact).

## Conventions

- **Branching:** none — a single `main` branch, no `develop`, no PR
  requirement. This is a deliberate deviation from the kit's default
  GitHubFlow assumption (see the top comment in `.github/workflows/ci.yml`).
- **CI runs on every push to `main`** (not on PRs — there are none):
  lint, typecheck, schema-drift, integration-tests, vuln-scan, ops-validate.
  See `.github/workflows/ci.yml`.
- **Testing:** acceptance-first, outside-in (`docs/development/Testing.md`)
  — write the test against the API before the feature code exists.
  Integration-tier-heavy by design; never mock the datastore.
- **Guardian tests:** `tests/integration/test_task_rollover_guardian.py`
  protects the deadline-rollover scheduling rule. Standing rule: change the
  rollover logic, update this suite in the same change.
- **Format / lint:** `just fmt` / `just lint` — ruff (backend), oxlint +
  prettier (frontend). `pre-commit install` once per clone; gitleaks, ruff,
  frontend lint/format, and schema-drift all run at commit time.
- **Schema changes:** edit `backend/app/models.py`, then
  `cd backend && .venv/bin/alembic revision --autogenerate -m "..."`,
  review the generated migration, apply via `just migrate`. Drift caught by
  `just schema-drift` (pre-commit hook + CI job, via `alembic check`).
- **Changelog:** `CHANGELOG.md` exists (Keep a Changelog format) but is not
  yet enforced — no release has happened, Pillar VII isn't adopted yet.
- **Docs:** `docs/design/` = what/why (Philosophy, Stakeholders);
  `docs/development/` = how (Getting-Started, Testing). Both currently
  marked "adopted" and reflect real, working setup.
- **Secrets:** never commit or print secrets. `.env` is gitignored;
  `.env.example` is the contract. gitleaks blocks secrets at commit time.
- **Agent-file sync:** no sibling agent files (GEMINI.md etc.) exist yet —
  create and sync them in the same commit if one is added.
- **License:** not yet chosen — still an open decision, not an oversight.

## Boundaries

Ask before, never assume: pushing, opening or merging PRs, tagging or
releasing, deploying, destructive data operations, anything touching
production, and adding new dependencies. Never print secrets or env-file
contents. On failure: stop, surface the raw error, and do not auto-recover
past it. Never create a commit without being explicitly asked in that
moment — a standing "yes, commit checkpoints like this" does not carry
forward to the next change.

## Gotchas — traps that have cost time

- **The local working directory is pinned by the coding-agent sandbox.**
  Renaming or moving this project's folder causes the agent's tool to
  silently recreate an empty directory at the old path and reset there.
  Don't rename the local folder — only the GitHub repo name is actually
  changeable.
- **Browser automation on a real Chrome profile risks autofill
  interference.** Driving this app's forms via browser automation triggered
  Chrome autofill mid-test, submitting an unintended value as a real
  project. Form inputs now set `autoComplete="off"` for this reason — don't
  remove it.
- **`DATABASE_URL` needs the explicit `postgresql+psycopg://` prefix**, not
  plain `postgresql://` — the latter defaults to the psycopg2 dialect,
  which isn't installed (this project uses psycopg3).
- **`db` vs `localhost` depends which side of the container boundary you're
  on.** Inside docker-compose, the `api` container reaches Postgres at host
  `db`. Anything run on the host (tests, manual `alembic` commands) must use
  `localhost` — same Postgres server, different hostname.
- **GitHub Action tags aren't uniformly spelled.** `aquasecurity/trivy-action`
  requires its `v` prefix (`@v0.36.0`); `actions/checkout` tolerates either.
  Verify the actual release tag before pinning — a plausible-looking version
  string can simply not exist.
- **Scanning a dev-only Docker image for vulnerabilities is close to
  meaningless.** `frontend/Dockerfile` runs `npm run dev` with every
  devDependency installed; that's why it's excluded from `vuln-scan` — add
  it back only once there's a real production build to scan instead.
